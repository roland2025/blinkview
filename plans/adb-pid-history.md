# Remember ADB PID→process-name history over time (Numba-backed)

## Context
Android recycles process IDs — PID 1234 might be `com.example.app` from T1 to T2, then a completely different process from T3 onward. Today, `AdbReader` (`io/adb_reader.py`) only keeps a **flat, non-historical** `self._process_ids: dict[str, int]` populated by one-shot `ps -A -o NAME,PID` snapshots (`_refresh_process_ids`, lines 393-416) that get silently overwritten — there is no record of *when* a PID belonged to which process. We want an efficient, Numba-backed structure that remembers this history, so a given log line's PID can be resolved to "whichever process actually owned it at that line's timestamp," not just whatever currently holds it.

Additionally: PID/TID are **already parsed out of every ADB log line** by `parse_adb_pid_tid` (`ops/codec_adb_long.py:213-266`) but the result is thrown away — `# out_b.pids[out_idx] = pid` is commented out (lines 258-260), and `LogBundle` has no `pids`/`tids` columns at all. This is a half-built hook we should finish wiring up as part of this work, since without PID reaching the log pipeline there's nothing to resolve against the new history table.

## Key design insight: this is low-churn, high-value data
Process launches/deaths happen far less often than log lines are emitted (churn is bounded by real-world process lifecycle events, not log throughput). This means the history table will always be small — rows scale with "how many times processes started/stopped/PIDs got reused" over a session, not with log volume. That rules out needing per-pid binary search over a large sorted array (the more complex option); a **hash-indexed backward linked list per PID** is simpler and just as fast, since any given PID will only have been reused a handful of times.

## Recommended design

### 1. Wire PID/TID into the existing pipeline (prerequisite)
- `core/types/log_batch.py`'s `LogBundle`: add dedicated `pids`/`tids` columns (`dtypes.ID_TYPE` or similar) with `has_pids`/`has_tids` flags, following the exact same optional-column pattern as `levels`/`modules`/`devices`.
  - **Why not reuse the existing `ext_u32_1`/`ext_u32_2` slots?** They cost the same memory either way (same dtype/size — the "existing" columns don't save anything, since two uint32 arrays are needed regardless of what they're called). But `ext_u32_1` already means "CAN arbitration ID" for CAN-sourced rows, and the central `CircularLogPool` merges rows from *all* active sources into shared segment arrays — if CAN and ADB are both active in one session, the same slot would mean two different things depending on which row it is. Dedicated `pids`/`tids` fields avoid that collision for the same cost.
- **Important prerequisite bug fix**: `copy_batch_to_segment` (`ops/segments.py:16-73`) — the function that merges a source's raw ingestion batch into the central pool's segments — currently only copies `rx_timestamps`/`timestamps`/`lengths`/`buffer` unconditionally and `levels`/`modules`/`devices` conditionally. It does **not** copy `ext_u32_1`/`ext_u32_2`/`ext_u64_1` at all today, meaning even CAN's existing arbitration-ID data never reaches the central pool the viewers read from. This function needs a new `if batch.has_pids: segment.pids[s_start:s_end] = batch.pids[b_start:b_end]` block (and same for `tids`) added alongside the existing conditional copies — otherwise the new columns would suffer the exact same silent-drop bug.
- `ops/codec_adb_long.py:258-260`: uncomment/finish `out_b.pids[out_idx] = pid; out_b.tids[out_idx] = tid` (currently disabled).
- Thread `has_pids`/`has_tids` through `NumpyBatchManager` (`core/numpy_batch_manager.py`, mirrors how `has_levels`/`has_modules`/`has_devices` are conditionally allocated) and `nb_bundle_push_len` (`ops/segments.py:280-331`, mirrors the existing `if bundle.has_levels: ...` blocks). Also update `CircularLogPool._rotate_segment` (`core/numpy_log.py`) to pass `has_pids=True`/`has_tids=True` when creating central segments, since the central bundle's flags are fixed at segment-creation time and shared by every source merged into it.

### 2. New `PidHistory` module — the "remember" structure
New files: `core/pid_history.py` (Python-facing class + growable arrays, mirrors `IndexedStringTable`'s structure in `core/id_registry/tables.py`) and `ops/pid_history.py` (Numba kernels).

**Storage** — flat, append-only, parallel arrays (one row per PID→name *transition*, not per log line):
- `pid[]` (uint32), `name_id[]` (uint32 — an ID into a reused `IndexedStringTable` interning process name strings, so repeated names like a relaunched app aren't duplicated), `valid_from[]` (int64 ns), `valid_until[]` (int64 ns, sentinel `OPEN` meaning "still alive as of last poll"), `prev_row[]` (int32 — backward link to this PID's previous interval, or `-1`).
- A hash index (open-addressing over `pid`, same linear-probing style as `IndexedStringTable`'s `nb_insert_item`/`nb_rebuild_index`, `core/id_registry/tables.py:20-86`) mapping `pid -> most_recent_row_index`.
- **Growth**: manual allocate-new/copy-swap doubling (`new_cap = max(needed, cap*2)`), matching `IDRegistry.register_new_modules`'s pattern (`core/id_registry/registry.py:110-122`) rather than `np.resize`, since `valid_until` needs a non-zero `OPEN` fill value on the newly-grown tail (same reason `IDRegistry` does it manually instead of via `np.resize`).

**Update — hybrid event-driven + poll-fallback:**

The primary trigger should be **event-driven, from data already flowing through the pipeline**, not a fixed-interval shell poll:

- Android's logcat already emits native process lifecycle events under the `ActivityManager` tag — lines like `Start proc <pid>:<name>/... for activity ...` and `Process <name> (pid <pid>) has died`. Since `AdbReader` already tails the full logcat stream (`io/adb_reader.py:262`), these lines are likely already flowing through the same parsing pipeline every other log line goes through — no extra `adb shell` round-trip needed to detect them. **This needs verifying during implementation**: confirm `AdbReader`'s current logcat invocation doesn't filter to a specific package/buffer that would exclude `ActivityManager` lines, and confirm the exact message format(s) actually seen (format has some drift across Android versions/OEMs — not perfectly stable).
- Add a small parser rule (same shape as `parsers/key_value.py`'s pattern, but simpler: match two known line shapes, extract `pid`+`name` or `pid`-only) that feeds start/death events directly into `PidHistory`'s update function as they're seen — same "append new row" / "close row" logic as below, just triggered per matching log line instead of per poll tick.
- Keep `AdbReader._refresh_process_ids()`'s `ps -A -o NAME,PID` (`io/adb_reader.py:393-416`) as a **coarse reconciliation fallback**, not the primary mechanism — run periodically via `core/task_manager.py`'s existing `run_periodic(interval_seconds, func, ...)` (already present, confirmed reusable as-is) at a much longer interval (e.g. 15-30s rather than every few seconds), to catch: processes already running before the log stream connected, any messages logcat dropped under buffer overflow, and `ActivityManager` format mismatches the parser rule doesn't recognize.
- Either signal (log-line event or poll diff) drives the same update path: for any `(pid, name)` that changed or disappeared, close its row (`valid_until[latest_row_for_pid] = event_or_poll_time`); for any new/changed `(pid, name)`, append a new row (intern `name` via the shared `IndexedStringTable`, set `valid_from = event_or_poll_time`, `valid_until = OPEN`, `prev_row = old latest_row_for_pid or -1`), and update the hash index.

**Query** — new Numba kernel `nb_resolve_pid_at(pid, timestamp) -> name_id` (style matches `nb_get_descendants`'s backward-chain walk, `ops/id_registry.py:15-36`):
- Hash-lookup `pid` to get the most recent row; walk backward via `prev_row` comparing `valid_from <= timestamp < (valid_until or now)` until a containing interval is found or the chain ends (`NOT_FOUND`). Chain length is bounded by how many times that specific PID was reused — expected O(1)-O(few), not something needing binary search.

### 3. Reused utilities (no reinvention)
- `core/task_manager.py`'s `run_periodic(interval_seconds, func, *args, **kwargs)` — confirmed to already exist and match exactly what the fallback poll needs; no new scheduling infrastructure required.
- `IndexedStringTable` (`core/id_registry/tables.py`) — reused as-is for interning process name strings (already generic, already has `fnv1a_64_fast`-based hashing).
- `IDRegistry`'s manual growth idiom (`core/id_registry/registry.py:110-122`) — copied for the PidHistory arrays' doubling.
- `nb_get_descendants`'s backward-chain-walk style (`ops/id_registry.py:15-36`) — template for the new `nb_resolve_pid_at` kernel's structure (raw arrays in, early-exit loop, `@app_njit()`).
- `ops/segments.py:79-104`'s `fast_find_first_ge/gt` were considered but **not used** — binary search doesn't pay off for the expected data shape (few rows per PID); noted here so it's clear this was a deliberate choice, not an oversight.

## Out of scope for this pass
- UI surfacing (a "Process" column in the log/table viewers, or wiring PID resolution into the `key=value` logfmt filter planned separately — see `logfmt-kv-filter.md`) — this plan covers the storage/remember/query engine and the minimal `LogBundle` wiring needed to feed it, not downstream display/filtering. Natural follow-up once this lands, and once it lands it should be able to plug directly into the logfmt filter's condition matching (e.g. `process=com.example.app`).
- Eviction/capacity bounding of the history table — given the low-churn characteristic described above, unbounded growth is expected to stay small for realistic sessions; add a cap later only if real usage shows otherwise.
- Exact `ActivityManager` message-format parsing across Android versions/OEMs — start with the common format(s), treat the poll fallback as the safety net for anything unrecognized rather than trying to handle every variant up front.
- Fallback poll interval tuning — start with a simple fixed interval (e.g. 15-30s, now that it's just reconciliation rather than the primary signal) via `task_manager.run_periodic`; make it configurable only if needed.

## Verification
- Unit tests for `PidHistory`: append/grow behavior (capacity doubling correctness, including the `OPEN` sentinel fill on newly-grown tail), diff-driven update logic (same pid+name extends, changed name closes+opens, disappeared name closes), and `nb_resolve_pid_at` correctness (single interval, multiple reused-PID intervals, timestamp before/after/inside each interval, unknown PID).
- Unit test for the `LogBundle` `pids`/`tids` wiring: construct a bundle with `has_pids=True`, run `parse_adb_pid_tid` against a sample "long" format logcat line, confirm `pids`/`tids` arrays are populated (mirrors existing kernel tests in `tests/test_ops_segments.py` style).
- Manual check (not run by the assistant): connect a real ADB device, restart an app a couple of times to force PID reuse, and confirm the history table's resolved name for a given PID/timestamp matches what was actually running at that time (cross-check against `adb shell ps` history if available, or timestamps of app restarts).
